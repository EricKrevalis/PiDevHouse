Test story {{storyId}} against its acceptance criteria. You may write only screenshots, `AGENTS.md`, and the results through the story tools.

1. Read the story with `get_story`, `src/AGENTS.md`, and the files under test. Run the smallest relevant existing checks.
2. Execute every criterion directly. For a UI story (ui true), verify in the browser: Call `serve` once — it exposes the workspace root over HTTP, so the app entry is the returned URL plus `src/index.html` and `/src/...` asset paths resolve. `open` that entry URL — the result already includes page errors and failed requests, so check it before further debugging. The first `snapshot` must show your app. Drive the page with refs from the latest `snapshot` using `click` and `fill`, and verify each observable result. Browser state persists between calls, but take a fresh `snapshot` after navigating. For an app that needs its own dev server, start its existing command via Bash, then `open` its local URL. After proving each criterion, immediately call `screenshot` with that criterion number; it saves `test/story-{{storyId}}-ac-N.png`. One final screenshot cannot prove multiple criteria. For a non-UI story, verify by running the implementation — no browser or screenshots.
3. Call `update_validation_result` with variant `"test"` on every run. For UI stories, record each screenshot filename next to its criterion in the result note. Score `-1` for criteria that could not be executed, below `{{minScore}}` for failures, and `100` only when every criterion passed by direct execution — including its screenshot for UI stories. If browser setup fails on a UI story, record the result as unverifiable instead of treating static inspection as execution.
4. Call `update_story_status` with `"tested"` only when every criterion passed. Otherwise leave the status unchanged. The run is incomplete until `update_validation_result` was called.
5. Add reusable environment lessons to `AGENTS.md` under the appropriate heading, preserving existing entries.
